# 账号停用与恢复

本文件说明当前账号访问控制的操作合同。执行真实账号变更仍须明确授权、目标环境及账号身份；本轮没有停用任何真实账号，也没有提供公开 Admin HTTP 接口。

## 访问语义

账号表 `"user".banned=true` 后，既有 cookie 不能继续取得该账号的私人 Site、素材、草稿或发布权限。Site 授权每次读取数据库状态，不依赖 cookie 中的旧用户对象。草稿写入条件重复检查账号状态；发布事务对账号行持有共享锁，停用更新与发布按数据库锁顺序生效。停用提交前已经完成授权的在途读取或写入可能先完成，不撤销已经发送的响应。

停用保留账号、Site、owner、grant、素材、草稿和不可变发布历史。公开页面仍读取原 Published；账号停用不是站点下架操作。需要撤销公开内容时，应另行明确下架范围，不能删除账号或素材代替。

该检查使用显式 `banned` 状态。不要仅设置过期时间，或假定后台会自动恢复账号。

## 授权后的运维步骤

1. 通过既有外置配置连接已经确认的目标数据库，核对数据库身份。不要把连接串、密码或私人交接文件放进仓库、PR 或命令行参数。
2. 用准确的账号 UUID 查询 `"user"`、`portfolio_users` 和 `sites` 的对应关系；同时核对用户名、slug 和现有停用状态。记录必要的变更前状态，避免仅凭显示名称选择账号。
3. 在事务内锁定目标账号行，按 UUID 更新 `banned=true`，确认恰好一行后提交。若条件不匹配或影响行数异常，回滚并停止。只改变访问状态，不删除业务关系。
4. 用受控的既有会话确认私人读取／保存／发布被拒绝，并核对其他账号和既有 Published。不要在聊天或日志中输出 cookie。
5. 若此次授权同时要求永久注销旧会话，在同一受控事务中按该账号 UUID 删除 `"session"` 行。单独设置 `banned` 会保留会话，恢复后未到期的旧 cookie 可重新使用；会话注销后必须重新登录。

## 恢复与回退

确认恢复授权与同一账号 UUID 后，事务内恢复原先允许访问的状态（通常为 `banned=false`，并清除不再适用的 `ban_reason`／`ban_expires`）。核对影响行数并提交，再验证账号读取与编辑权限。恢复不重新开户、不重写 Site、不重新授予模板，也不改 Published。

若停用操作选错目标，按记录恢复该行原值；已经撤销的会话无法恢复，需重新登录。应用代码回退不会自动改变数据库中的停用状态；回退到缺少此检查的旧版本会失去这里描述的即时拒绝保证，应先评估访问风险。

## 验证范围

专用 PostgreSQL 集成测试覆盖旧会话停用／恢复、Site 保留、其他账号不受影响及发布事务拒绝。最终远端验收以对应 PR Head 的完整 CI 为准。
