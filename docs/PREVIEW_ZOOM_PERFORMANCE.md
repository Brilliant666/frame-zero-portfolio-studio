# 有界面 Chrome：进场后连续缩放归因与有限修复

## 结论与范围

基于 `88d63e0` 工作树，最终仅保留镜头运动期间的 `will-change: transform`，停止 150ms 后恢复原值，卸载时清理。没有改变设计、阴影、毛玻璃、照片数量/资源清晰度或动画时长。其余实验全部撤回。仅新版 Composer 使用此实现，原版模板样式没有改动。

**掉帧率六组中位数全部低于 5%，但整轮验收不能标为全通过**：最终 DPR1/A/第1次记录到 337.4ms 的 long-animation-frame；没有删掉此样本。该窗口最长被记录的 FunctionCall 仅 0.793ms，LoAF scripts 为空、blockingDuration=0，rAF 同时存在 337.5ms 间隔，尚不能定位该帧的具体调度/呈现原因，更不能无证据归咎操作系统。

## 测量校准

- 有界面 Chrome 154.0.8037.57，1440×900 CSS viewport，deviceScaleFactor 分别 1/2。Windows 报告刷新率319Hz，约320Hz；用户已明确取消60Hz及GPU硬件加速的强制要求。没有更改显示器设置。
- `chrome://gpu` 截图确认 Canvas/Compositing/Rasterization 硬件加速；没有使用 headless 数字作为通过依据。
- 本机正式预览构建3002，读取相同11张照片，使用隔离API fixture、独立浏览器上下文，拦截所有非GET内容请求。不修改用户内容或localStorage。
- 未悬停预热；照片服务缓存已复用，浏览器上下文每次新建，不声称全冷缓存。每组5次；trace开启，不同时录屏，不并行构建/测试压CPU。
- A：点封面后约300ms，5次Ctrl+=、间隔100ms；B：点击后约3000ms执行同样输入；C：A时点，5次CDP标准鼠标滚轮事件，deltaY=-120、pixel单位、无Ctrl。C是事件回放，不冒充实体鼠标滚轮验收。
- CDP传输有延迟，实际首次输入相对点击及5次事件时间点写入每个JSON；典型A为307–322ms，C为315–332ms。
- 统计从首次输入的Performance mark，到最后一次镜头transform变化，不使用固定1.5秒或静止后窗凑分母。静止250ms后确认结束；DrawFrame少于30判无效。本轮所有正式样本有效，最终最少287个DrawFrame。
- 掉帧口径 DroppedFrame/(DrawFrame+DroppedFrame)。同时PerformanceObserver记录`long-animation-frame`，按与测量窗口相交的帧统计>50ms和>100ms；没有用掉帧比例替代长帧。

### 归因边界

控制组整个运动窗FunctionCall累计中位31.33ms、Paint累计7.75ms；will-change组分别32.67ms、8.12ms，脚本和主线程Paint累计没有明显减少，但合成帧掉帧显著下降。证据支持**运动画布合成/栅格策略**为有效优化位置，不支持“长JS任务是主要原因”的判断，也不把未采样的GPU内部阶段伪装为已精确定位。

基线DPR2的15个A/B/C运动窗口，高档1100/2200请求以及高档图片load均为0。A的镜头在现有1600ms保护期内结束，B/C中已有合并检查没有在运动窗发起高档请求。额外guard未改善A，因此按要求撤回；这不保证任意持续拖拽与任意网络时序都绝不会换图，后者不扩成此次改造。

## 实现与验证

- `use-composer-motion`仅在任务开始/结束通知DOM生命周期，不增加每帧React state。连续缩放取消旧清理计时器，自然结束、stop、减少动态效果、隐藏和卸载均有清理路径。
- `createMotionActivity`在运动中设transform提示，停止150ms后恢复原will-change，允许静止重新栅格；卸载立即恢复。
- 本机A/B保留一个`preview:motion-diagnostic=off` sessionStorage开关。只关闭优化，不开放生产访问、不开公网诊断入口，正常默认开启优化。原先无效实验不留在代码中。
- 3项真实helper测试覆盖149/150ms、继续运动取消旧timer、卸载恢复、local-only开关。完整npm test **501项通过**；lint、TypeScript、普通Next与legacy构建预算、本机正式预览构建通过。未修改任何CSS文件的最终内容。
- 性能测量完成后按用户后续授权提交并推送；未改PR状态、未合并或部署。
